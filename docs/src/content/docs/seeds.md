title: Seeds
description: "Data for a database, declared in the project and applied by the app through the model's use cases: records written out, and records generated by the hundred for demos."
---

The [seed](/esquadro/blueprints/reference/seed/) blueprint puts data in a
database from `seeds/*.yaml`, the project's: what a new database starts
with (categories, settings) and the data of a demo (hundreds of orders over
the last months). Each record goes through its module's use case, as the
API's do: the model's validations and defaults hold.

```sh
task seed                 # <app> seed: every seeds/*.yaml, in the order of their names
task seed -- --fresh      # delete the lists' records, and apply everything again
<app> seed --dry-run      # check everything, write nothing
<app> seed seeds/02-sales.yaml
```

## Records written out

A file is lists by their names in the API (`categories`, `ad_results`), each
its records, with the fields of the API's JSON:

```yaml
categories:
  - $id: home              # an alias, for other records to point at
    name: Home
  - $id: garden
    name: Garden

products:
  - name: Lamp
    price: "49.90"         # in the app's currency, or { amount: "49.90", currency: BRL }
    status: ACTIVE
    category: $home        # a relation, by its alias (or category_id: <uuid>)
    created_at: 2026-10-01 # a date in the past
```

A record keeps its id between runs (from its alias, or its place in the
file): applying the seed again creates what is missing, and leaves what is
there as it is.

## Records generated

```yaml
orders:
  generate: 500
  fields:
    number:     { sequence: "#{n:5}" }                 # #00001, #00002…
    status:     { pick: { PAID: 4, PENDING: 1, FAILED: 1 } }
    total:      { money: 40..500 }
    quantity:   { int: 1..3 }
    product:    { one_of: [Shirt, Shoes, Backpack] }
    customer:   { any: true }                          # a record already there, at random
    created_at: { past: 90d, trend: up }               # more of them lately
```

| Rule | Makes |
|---|---|
| a value | that value, for every record |
| `sequence: "#{n:5}"` | numbered values, padded |
| `pick: [A, B]`, `pick: { A: 3, B: 1 }` | one of the values, evenly or by weight (aliases too: `[$home, $garden]`) |
| `one_of: [...]` | one of the values |
| `int: 1..10`, `decimal: 0.5..9.99`, `money: 10..500` | a number in the range |
| `past: 90d`, `future: 2w`, `between: [2026-01-01, 2026-06-30]` | a moment; `trend: up` puts more near now, `down` far from it |
| `any: true` | a record of the relation's list, at random |
| `name`, `email`, `sentence`, `words: 3` | a person's name, an email, text |
| `null: 0.2` | with any rule: empty one time in five |

A field not named is made by its type and its name: an enum's value, a
number within the model's `min` and `max`, a date of the last 30 days, a
record of a relation, a person's name for a list of people, an email, a
city, a country, a sentence for a description; the optional ones are empty
now and then, and unique ones are numbered. The words are in the language
of the app's frontend (`pt_br`, `en`).

The same file makes the same records (`--seed 7` for others). A list that
has records already is not generated again: `--fresh` deletes the files'
lists first (the ones that point at others first), and starts over.

## Safety

- Each file is applied in a transaction: a mistake undoes that file.
- In production (`APP_ENV=production`) the seed is refused without
  `--allow-production`, and `--fresh` never runs there.
- `esquadro check` reads the seed files against the model: a list or a
  field that does not exist, an enum's value, a whole number or a date
  that is not one, an alias used before it is declared, a rule it does not
  know, each at its file and line.
- Files are not sent by a seed (a `file` or `image` field stays empty), and
  the people who sign in are made with `<app> security`, not by a seed.

`esquadro new` writes `seeds/01-example.yaml`, generating a few records of
each list: `task seed` fills a new project's database at once.
